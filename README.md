# q0t-gates 🛡

Движок принуждения правил для Claude Code. Превращает «правило, которое периодически
проёбывается» в гейт, который нельзя забыть.

## Зачем

В воркспейсах QB и Cowork было заявлено 11 обязательных правил. Принуждались **два** —
`preflight` перед коммитом и guard на write-SQL. Оба реализованы кодом (хуки), и ровно они
не нарушались. Остальные девять жили в промте.

Промпт — это просьба. Просьбу можно не выполнить, и она не выполняется.

**Правило, которое должно соблюдаться всегда, обязано быть кодом.** Промпт остаётся для того,
что требует суждения; гейт — для того, что можно проверить.

## Почему движок, а не просто хуки

Движок работает *поверх* хуков: хук — способ доставки события, движок решает, что с событием
делать. Что даёт слой поверх:

- **Наследование.** Хуки Claude Code не каскадируются по дереву директорий — они читаются из
  `~/.claude/settings.json` и из корня сессии. Правило, положенное в `QB/`, само по себе не
  подействует в `QB/accountant_web/`. Движок поднимается по дереву сам.
- **Один процесс вместо N.** Девять правил на `PreToolUse` в чистых хуках = девять записей в
  `settings.json`, и харнесс запускает все девять на каждый вызов Bash. У хуков стоимость
  линейна по числу правил, у движка — константа: 13 мс на быстром пути независимо от того,
  правил три или тридцать.
- **Единый аудит.** Каждый bash-хук пишет лог как захочет или не пишет вовсе. Без общего
  формата нечего агрегировать — а «какие гейты работают, а какие мешают» должно быть
  метрикой, а не ощущением.
- **Цена одного правила.** Хук: написать скрипт, распарсить JSON, вписать в 29-килобайтный
  `settings.json`, не сломав его, самому продумать блокировку и логирование — около часа.
  Движок: положить файл на 8 строк. Цена правила определяет их количество; при цене в час
  их два.

Чего движок **не** даёт: новых точек перехвата (только события Claude Code) и скорости на
одном-единственном правиле. Окупается начиная примерно с трёх-четырёх правил на событие.

## Установка

```bash
cd ~/Developer/q0t-gates
make build      # собирает bin/gate и bin/gates
make install    # регистрирует хук в ~/.claude/settings.json (с бэкапом)
```

Регистрация глобальная и одноразовая. Активность определяется не настройками, а наличием
файлов правил: **подключить движок к проекту = положить туда файл правила.**

## Как это работает

```
событие хука (stdin JSON)
   ↓
быстрый путь: есть ли вообще правила в дереве?   → нет → выход, 13 мс
   ↓
каскад: собрать правила от global вниз к файлу
   ↓
[[match]] — смотрит ли правило на это событие
   ↓
[check] — нарушено ли
   ↓
[escape] — есть ли законный обход
   ↓
вердикт: block / ask / warn  +  запись в журнал
```

## Каскад

```
~/Developer/q0t-gates/global/*.toml                  ← везде, всегда
    ↓
~/Developer/QB/.claude/gates/*.toml                  ← вся работа в QB
    ↓
~/Developer/QB/accountant_web/.claude/gates/*.toml   ← только этот сервис
```

Правило с тем же `id` ниже по дереву перекрывает верхнее — так подпроект ослабляет severity
или выключает унаследованное правило:

```toml
# accountant_web/.claude/gates/no-llm-attribution.toml
disabled = true
reason   = "форк вендорского кода, атрибуция в истории легитимна"
```

Подъём останавливается на `$HOME`.

Для правок файлов (`Edit`/`Write`) отсчёт каскада идёт **от директории редактируемого файла**,
а не от cwd сессии: иначе правило подпроекта не сработает, когда его файл правят из корня
воркспейса — а это основной способ работы.

## Как добавить правило

Один файл — одно правило. `id` = имя файла.

```bash
$EDITOR ~/Developer/q0t-gates/library/my-rule.toml
gates check                          # правило парсится?
gates enable my-rule ~/Developer/QB  # симлинк в проект
gates enable --global my-rule        # или везде
```

Новое правило заезжает в `severity = "warn"`. Через неделю смотришь `gates audit` — если
ложных срабатываний нет, меняешь одну строку на `block`.

### Схема

| Поле | Обяз. | Значения |
|---|---|---|
| `description` | да | зачем правило существует |
| `event` | да | `PreToolUse` `PostToolUse` `Stop` `SubagentStop` `UserPromptSubmit` |
| `type` | да | `pattern` `script` `judge` |
| `severity` | да | `block` `ask` `warn` |
| `message` | да | что увидит агент при срабатывании |
| `[[match]]` | нет | когда правило смотрит; пусто = всегда на этом событии |
| `[check]` | да | условие нарушения |
| `[escape]` | нет | легальный обход с аудит-следом |
| `disabled` | нет | `true` выключает унаследованное правило; требует `reason` |
| `fail_closed` | нет | `true` — при ошибке движка правило блокирует, а не пропускает |

`type` указывается всегда и явно: неявный дефолт в DSL — это скрытое поведение, которое потом
стоит часов отладки.

### `[[match]]` — массив таблиц

**ИЛИ между блоками, И внутри блока.** Один блок не покрывает все способы сделать одно и то же:

```toml
[[match]]
tool    = "Bash"
command = '^\s*git\s+commit\b'

[[match]]
tool = ["mcp__gitlab-qb__*", "mcp__github__create_or_update_file"]
```

`tool` принимает строку или список, поддерживает glob — без этого каждый новый MCP-сервер
тихо открывает дыру в каждом правиле. Остальные ключи блока — имена источников, значения —
регекспы.

### Источники

Правило описывает, **что** проверяем, а не **как** достаём: `commit_message` одинаково
извлекается из `git commit -m` и из аргументов MCP-инструмента.

| Источник | Что отдаёт |
|---|---|
| `command` | `tool_input.command` |
| `tool_input` | весь JSON инструмента как текст |
| `staged_diff` | `git diff --staged` в cwd |
| `git_remote` | вывод `git remote -v` — принадлежность репозитория по факту, а не по расположению |
| `git_branch` | текущая ветка |
| `commit_message` | сообщение коммита — из Bash или из MCP |
| `transcript` | текст сессии, только основной контекст |
| `transcript.all` | то же, включая субагентов |
| `transcript.tools` | вызванные инструменты и скиллы (`Skill(postmortem)`), основной контекст |
| `transcript.tools.all` | то же, включая субагентов |
| `prompt` | текст промпта (`UserPromptSubmit`) |
| `in_subagent` | `true` / `false` — вызов идёт из субагента |
| `file:<path>` | содержимое файла относительно cwd |

Источники вычисляются лениво: `staged_diff` не запускает git, если ни одно правило его не просит.

### Матчинг по факту, а не по расположению

Каскад привязывает правило к дереву директорий. Но «рабочий репозиторий» — это не место
на диске, а факт: куда смотрит remote. Репозиторий, лежащий вне `~/Developer/QB`, каскадом
не покроется.

```toml
[[match]]
tool       = "Bash"
command    = '^\s*git\s+commit\b'
git_remote = 'gitlab\.loc|qbrains'
```

Такое правило действует в любом каталоге, чей remote указывает на рабочий GitLab, и не
действует в личных проектах — при этом ни человеку, ни модели не нужно нигде записывать
«каталог X относится к работе». Это ответ на известную слабость моделей: они плохо
склеивают два разнесённых факта («в QB нельзя X» + «репозиторий Y относится к QB»).
Гейт не склеивает — он проверяет.

### Три типа проверки

**`pattern`** — регексп по источнику. `deny_if` (нарушение, если нашлось) либо `require`
(нарушение, если не нашлось).

```toml
[check]
source  = "commit_message"
deny_if = '(?i)Co-Authored-By:\s*Claude'
```

**`script`** — когда регексп не выражает: например, нужен порядок событий, а не факт их наличия.

```toml
[check]
script = "checks/vault_searched_first.py"
```

Скрипт получает на stdin `{"event": <исходное событие>, "sources": {...}}`, печатает
`{"violated": bool, "reason": "..."}`. Ненулевой код или непарсимый вывод → правило считается
**не** сработавшим, в журнал идёт `error`.

**`judge`** — когда важен не факт, а качество.

```toml
[check]
model   = "haiku"
input   = ["transcript"]
timeout = 30
prompt  = "Доведена ли причина до конкретной строки кода? Ответь JSON {violated, reason}"
```

Вердикт судьи валидируется по фиксированной форме. Таймаут или мусор → `judge_failed`,
правило не срабатывает: судья не должен уметь заблокировать работу собственной поломкой.

### `severity`

| | `PreToolUse` / `PostToolUse` | `Stop` |
|---|---|---|
| `block` | действие не происходит | сессия не закрывается |
| `ask` | решает человек | решает человек |
| `warn` | действие идёт, сообщение показывается | сессия закрывается, сообщение показывается |

### `escape` — разовый обход с аудит-следом

```toml
[escape]
source = "commit_message"
marker = "[allow-env]"
```

Правило сработало, но маркер найден → действие пропускается, в журнал идёт `escaped`.

Смысл двойной: система без выхода отключается целиком при первом ложном срабатывании, а
обходы в журнале — данные. «Гейт обходили 9 раз, всегда на `*.template`» означает, что чинить
надо регексп, а не человека.

**Маркер ищется только там, где пишет человек** — `prompt` или `commit_message`. Любой другой
источник движок отвергает на загрузке правила: иначе агент упрётся в гейт, выпишет себе
амнистию и поедет дальше, а ты будешь думать, что система работает.

Для `commit_message` движок различает, кто вписал маркер. Если санкции в твоих сообщениях не
было, запись идёт как `escaped_by_agent` и в сводке видна отдельной строкой.

## Журнал

`audit/YYYY-MM.jsonl`, одна строка на срабатывание. `passed` не пишется — иначе журнал
зарастёт отметкой о каждом вызове инструмента, а полезный сигнал в нём утонет.

```bash
gates audit           # сводка за текущий месяц
gates audit 2026-08
```

| verdict | Что значит |
|---|---|
| `violated` | правило сработало |
| `escaped` | обошли законно, санкция человека была |
| `escaped_by_agent` | маркер в коммите вписан без санкции в твоих сообщениях |
| `judge_failed` | судья не ответил или ответил мусором |
| `error` | битое правило, упавший скрипт, сбой движка |

## Команды

```
gates list [dir]           действующие правила для директории
gates library              что лежит на складе и где активировано
gates enable <id> [dir]    активировать правило в проекте
gates enable --global <id> активировать везде
gates disable <id> [dir]   снять активацию
gates check                распарсить все правила (для CI)
gates audit [YYYY-MM]      сводка журнала
```

## Отказоустойчивость

**Fail-open.** Любое необработанное исключение → действие разрешается, в журнал `error`.
Гейт, который ломает работу собственным багом, будет отключён целиком в первый же день, и
защиты не останется вовсе. Правило может потребовать обратного через `fail_closed = true`.

Битое правило не роняет остальные: оно пропускается, ошибка уходит в журнал.

`CLAUDE_GATES_DISABLE=1` полностью выключает движок для процесса — этим же движок защищается
от рекурсии, когда судью запускает `claude -p`.

## Разработка

```bash
make test     # юниты + e2e на собранном бинаре
make check    # go vet + валидация всех правил
make build
```

Правило без golden-случаев в `tests/library_test.go` не проходит тесты — это намеренно:
набор правил без тестов становится неревьюируемым за пару месяцев, то есть болеет ровно тем,
от чего лечит промпт.

## Что дальше

Это подсистема **A** из четырёх:

- **A — enforcement** (этот репозиторий)
- **B — ревью-панель и реестр находок**: независимый архитектурный ревьюер, тех.долг как
  артефакт, а не реплика в чате
- **C — отчётность и эскалация**: сводки наверх; журнал этого движка — источник данных
- **D — оркестратор**: агрегирующий слой между человеком и исполнителями
