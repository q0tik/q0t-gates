# Архитектурное ревью и реестр тех.долга

Спека лежит рядом со спекой A, потому что B принуждается гейтом из A и без него
превращается в ещё одну просьбу в промте.

## Зачем

За что платят разработчику, кроме скорости: **чтобы цена изменений не росла**. Этот контур
сейчас не закрыт ничем. Есть `/code-review` — он читает диф и ищет баги в строках. Никто не
смотрит, что происходит с формой системы: появляются ли зависимости, которых не было;
дублируются ли решения; какие прошлые решения отменяются молча.

Второе: находки, сказанные в чат, не существуют. Через неделю окно закрыто, и ничего не
осталось. Разбор без артефакта — это разговор.

## Границы

**Входит:** субагент-архитектор, скилл ревью, реестр находок в vault, гейт принуждения,
метрика полезности ревьюера.

**Не входит:**
- бизнес-ревьюер и ревьюер-программист. Программист уже есть — это `/code-review`.
  Бизнес-ревьюер без машиночитаемых требований выродится в пересказ тикета;
- методология (DDD/TDD) в промпте роли. Методология в роли даёт стилистику, а не результат.
  Проверяемое требование делается гейтом: «в коммите с логикой есть изменённый тест» — шесть
  строк TOML вместо роли;
- второй ревьюер любого рода до того, как у первого будет измеренная польза.

## Архитектура

Четыре компонента, каждый со своей ответственностью:

| Компонент | Где | Что делает |
|---|---|---|
| субагент `architect` | `QB/.claude/agents/architect.md` | смотрит на форму системы, возвращает находки текстом |
| скилл `architect-review` | `QB/.claude/skills/architect-review/` | протокол: собрать вход → позвать агента → дедуп → записать |
| реестр | `qb/debt/` в vault | одна находка = одна заметка со статусом |
| гейт `architecture-review-required` | `q0t-gates/library/` | структурный диф без ревью не уезжает в MR |

Гейт **не запускает** ревью. Хук не может гонять агента по коду минутами; он проверяет факт,
как `preflight`. Работу делает скилл.

### Поток

```
структурное изменение готово
   ↓
git commit / MR  →  гейт: был ли Skill(architect-review)?
   ↓ нет
скилл architect-review
   ├─ строит карту модулей (tools/modmap.py)
   ├─ собирает изменения ФОРМЫ (diff --stat + публичные символы)
   ├─ читает decisions/ и открытые debt/ по сервису
   ├─ зовёт субагента architect
   ├─ дедуп: что из находок уже в реестре
   └─ основной контекст пишет новые заметки в qb/debt/
   ↓
коммит проходит
```

Запись в vault делает **основной контекст, а не субагент** — по действующей конвенции QB
(чтение делегируется, запись остаётся наверху). Заодно ты видишь, что записывается.

## Вход архитектора — не диф

Главное решение спеки. **Если дать архитектору тело дифа, он скатится в code review** и будет
находить то же, что встроенный ревьюер, только дороже. Ограничение входа и есть механизм,
который заставляет смотреть на структуру.

Что получает:

| Вход | Источник |
|---|---|
| карта модулей сервиса | `tools/modmap.py <service>` |
| `git diff --stat --staged` | какие файлы тронуты и насколько |
| изменения публичных символов | `git diff -U0` отфильтрованный по сигнатурам |
| новые зависимости | диф `requirements.txt` / `go.mod` / `package.json` |
| решения по сервису | `decisions/` из vault |
| **открытые находки по сервису** | `debt/` из vault — обязательно, см. дедуп |
| `CLAUDE.md` сервиса | если есть |

Чего не получает: тела дифа, содержимого функций, логов, тестов.

### Карта модулей

Строится скриптом, а не чтением 85 файлов агентом: дёшево, повторяемо, одинаково от запуска
к запуску.

`tools/modmap.py <path>` печатает:

```
## Дерево (без тестов, venv, миграций-данных)
routers/alerts.py, services/janus_client.py, …

## Эндпоинты
POST /api/alerts/settings        routers/alerts.py:41
GET  /api/alerts                 routers/alerts.py:12

## Публичные символы верхнего уровня
class AlertsService            services/alerts.py:18
def  get_janus_executions      sdk/janus.py:77

## Межсервисные вызовы
httpx → conf-service           services/conf.py:22
call_pg_proc → insert_janus_*  sdk/janus.py:91

## Зависимости
fastapi, psycopg2, httpx, …
```

Python — первый класс (regexp по `def`/`class`/`@router`/`@app`); для прочих языков
деградирует до дерева и зависимостей, не падая.

## Вопрос — не «проверь»

Субагент отвечает ровно на четыре вопроса. Общая формулировка «найди проблемы» даёт пересказ
кода; конкретный вопрос даёт находку.

1. **Новая связность.** Появилась ли зависимость между модулями или сервисами, которой не
   было? Стала ли существующая двусторонней?
2. **Дублирование решения.** Есть ли в системе механизм, уже делающий то же самое? Это главный
   источник роста цены: два способа делать одно расходятся и требуют двойных правок вечно.
3. **Что станет дороже менять.** Какое будущее изменение это удорожает и насколько конкретно.
4. **Затронутые решения.** Какие записи из `decisions/` это изменение отменяет, обходит или
   противоречит им. Тот самый композиционный вопрос: факт записан, но сам собой никем не
   вспомнится.

На каждый вопрос допустим ответ «нечего сказать» — и он ожидаем. Ревьюер, который на каждом
ревью находит что-то по всем четырём пунктам, не работает, а сочиняет.

### Формат ответа субагента

```json
{
  "findings": [
    {
      "question": 1,
      "title": "accountant_web ходит в janus напрямую, минуя SDK",
      "why_expensive": "смена контракта janus теперь требует правок в двух местах…",
      "what_to_do": "перенести вызов в accountant_lib…",
      "severity": "medium",
      "duplicates": "debt/2026-07-14-janus-direct-calls.md | null"
    }
  ],
  "nothing_to_say": [2, 3]
}
```

`duplicates` заполняет сам субагент — он получает открытые находки на вход и обязан отметить,
что повторяет. Без этого реестр зарастёт дублями за две недели, и его перестанут читать.

## Реестр `qb/debt/`

Одна находка — одна заметка. Новая папка в vault, заведена с согласия владельца.

```markdown
---
type: debt
service: janus
created: 2026-08-27
updated: 2026-08-27
severity: high | medium | low
status: open | accepted | rejected | fixed
source: architect-review
trigger: BSGD-4547
related: ["decisions/2026-06-19-janus-event-driven"]
---

## Что

## Почему это дорого

## Что сделать

## Отвергнуто, потому что
<!-- заполняется при status: rejected — одной строкой, без церемоний -->
```

`status` — не украшение, а канал обратной связи ревьюеру:

| status | Значение |
|---|---|
| `open` | записано, решения нет |
| `accepted` | согласен, надо чинить (дальше — руками в Jira, если дозрело) |
| `rejected` | архитектор промахнулся; одной строкой почему |
| `fixed` | починено |

Повышение находки до тикета Jira — **вручную и по решению человека**. Автоматическое
заведение тикетов засорит командный бэклог гипотезами агента и будет видно коллегам.

## Гейт

```toml
description = "Структурное изменение уезжает в MR без архитектурного ревью"
event    = "PreToolUse"
type     = "script"
severity = "warn"
message  = """Изменение меняет форму системы (новый модуль/эндпоинт/таблица/зависимость),
а архитектурного ревью не было. Вызови skill `architect-review`.
Если структурная правка тривиальна — [skip-architecture] в сообщении коммита."""

[[match]]
tool    = "Bash"
command = '^\s*git\s+commit\b'

[[match]]
tool = "mcp__gitlab-qb__*"

[check]
script = "checks/architecture_review_required.py"

[escape]
source = "commit_message"
marker = "[skip-architecture]"
```

Скрипт признаёт изменение структурным, если в `staged_diff` есть хоть одно:

- новый файл с кодом — не тест, не конфиг, не миграция-данных;
- новый эндпоинт: `@router.`, `@app.`, `APIRouter(`;
- DDL или миграция схемы: `CREATE TABLE`, `ALTER TABLE`, `migrations/`;
- новый межсервисный вызов: новый базовый URL, новый httpx/requests-клиент;
- новая зависимость в `requirements.txt` / `go.mod` / `package.json`.

Нарушение = структурный диф **и** отсутствие `Skill(architect-review)` в
`transcript.tools`. Сигналы берутся из дифа, а не из речи — здесь лексика ни при чём.

## Метрика: работает ли ревьюер вообще

Единственная честная проверка — **доля `accepted` среди закрытых находок**. Ниже 30% ревьюер
не нужен: он производит текст, который научишься пролистывать, и тогда он вреднее отсутствия.

Команда `/debt` (в `QB/.claude/commands/`) читает frontmatter и печатает:

```
qb/debt — 14 находок

статус        всего
open              5
accepted          6
rejected          2
fixed             1

принято: 6/9 закрытых (67%)   ← ниже 30% значит чинить вопросы, а не плодить роли
по сервисам: janus 5, accountant_web 4, stevia 3, …
severity: high 2, medium 8, low 4
```

Та же логика, что у `gates audit`: судьба инструмента решается цифрой, а не ощущением.

## Стоимость

Запуск на каждое структурное изменение — это агент, читающий карту и отвечающий на четыре
вопроса: единицы минут и заметные токены. Поэтому:

- гейт срабатывает только на структурных изменениях, а их меньшинство;
- вход ограничен картой, а не кодом — агент не читает 85 файлов;
- карту строит скрипт, а не модель.

Если окажется дорого — первым делом сужать критерий структурности, а не отключать ревью.

## Раскатка

**Этап 1.** `tools/modmap.py`, субагент, скилл. Без гейта. Запускается руками:
`/architect-review` на нескольких недавних задачах — проверить, что находки осмысленные.

**Этап 2.** Папка `qb/debt/`, формат заметки, команда `/debt`. Записать находки первого этапа.

**Этап 3.** Гейт в `warn` — две недели. Смотрим `gates audit`: как часто срабатывает, не ловит
ли тривиальные правки.

**Этап 4.** Решение по метрике:
- принято ≥ 30% → гейт в `block`, думаем про второго ревьюера с другим входом;
- принято < 30% → чиним вопросы и вход. Второго ревьюера не заводим.

## Риски

| Риск | Митигация |
|---|---|
| Архитектор без дифа не понимает сути изменения и фантазирует | на вход идут изменения публичных символов и `--stat` — форма изменения видна, содержимое нет |
| Одни и те же находки на каждом ревью | открытые находки подаются на вход, субагент обязан заполнить `duplicates` |
| Реестр растёт, никто не разбирает | `/debt` показывает `open`; ревью начинается с показа открытых по сервису |
| Ревьюер шумит, его игнорируют | метрика и порог 30%, решение на этапе 4 |
| Гейт ловит тривиальные правки | `escape` с маркером; при частых обходах — сужать критерий, обходы видны в журнале |
| Стоимость на каждое структурное изменение | критерий структурности, ограниченный вход, карта скриптом |
| Соблазн добавить ролей до измерения пользы | явно вынесено за границы спеки |

## Открытые вопросы

**Личные проекты.** Реестр спроектирован в `qb/`, то есть под работу. Для личных репозиториев
места пока нет и решения тоже: заводить ли `debt/` в корне vault — отдельный разговор, папки
верхнего уровня заводятся только с явного согласия. До тех пор B работает в QB.
